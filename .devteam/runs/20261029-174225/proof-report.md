## Assumptions

Decided on the builder's behalf (change any that are wrong):

- Search stays controlled only by the existing per-instance searchEnabled prop: no global config-provider switch, no runtime button and no keyboard shortcut to reveal it.
- When search is off, any active search term is dropped so the menu is never left filtered by a term the user can no longer see, and no empty-results state is shown while search is hidden.
- Enabling search keeps 1.7.0's look and behaviour exactly: default placeholder 'Search menu...', autofocus default true, custom icon, filtering, and numbered shortcuts over the filtered list.

## Out of scope

- A visible toggle, button or '/' shortcut that reveals search at runtime; only the prop turns it on.
- A global searchEnabled option on ZestSidekickConfigProvider.
- Changing search matching (searchTerms, label matching) or result ordering.
- Storing a per-user or per-app preference for search in localStorage or sessionStorage.
- Changing the search input's markup, accessible name or styling beyond hiding it by default.

## Role documentation

### Analyst: requirements

Turn the SidekickMenu search box from on-by-default to opt-in: a consumer who renders <SidekickMenu items={items} /> sees no search input, and search appears only when the consumer passes searchEnabled={true}. Existing installations get the hidden default just by upgrading, because the default is resolved in code, not stored anywhere. Enabling search keeps every 1.7.0 search behaviour; no new prop is added. Because the default changes, the release must be a major version with a migration note and the reference docs updated.

### Architect: design

The change is a one-literal default flip plus a tiny cleanup effect inside the existing SidekickMenu orchestrator, not a new feature. In SidekickMenu.tsx change the destructured default from `searchEnabled = true` to `searchEnabled = false`; the existing render guard `searchEnabled && !effectiveRailCollapsed` then stops mounting the input, its ref stays null, and the existing autofocus effect already no-ops on a null ref, so no new focus code is needed and nothing invisible is focusable. If the prop changes from true to false while a term is still held, the list must not stay filtered by a term the user can no longer see: a second effect dispatches SET_SEARCH_TERM with an empty string when search is off and the term is non-empty. SET_SEARCH_TERM already exists in menuReducer, and the existing pre-search path effect restores the section once the term empties, so no reducer or context change is needed. Enabled search keeps the same lookup, placeholder, icon, autofocus, empty-state, arrow-key and numbered-shortcut code paths untouched, because only the default value and the off-state term reset change. Public surface is unchanged: no export, prop name or type is added, removed or renamed; SidekickMenuProps.searchEnabled stays `boolean | undefined` and only its documented default flips, so UI/index.ts is not touched. This is a behaviour-breaking change for consumers, so package.json goes to 2.0.0, docs/breaking-changes.md gets a v2.0.0 entry naming searchEnabled with the searchEnabled={true} migration, and README.md, docs/api.md, docs/configuration.md, docs/examples.md and docs/features.md stop presenting search as on by default while keeping their prev/next links.
